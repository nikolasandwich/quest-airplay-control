# 校准体验失败复盘（0.2.11–0.2.13）

2026-09-12。结论：这是交互与实现验收失败，不是用户不会操作。我们把需要稳定识别、特定方向和速度的实验测量流程直接变成了用户必须完成的操作，又连续交付局部修补。编译、单测和页面尺寸检查通过，不能证明用户能顺利完成。

本次只读日志与源码，没有重启、重连、安装或发输入。设备仍为0.2.13；未部署的自然学习草稿已单独保存，停止继续叠加功能。本文件提出的修复尚未实施。

## 为什么圆环跑、识别卡、动作不算

| 问题 | 已确认的证据 | 尚不能确认的部分 |
|---|---|---|
| 追圈与过关规则不一致（设计） | 网页要求向圆环移动；`PointerCalibration.acceptGuided()`只检查方向/幅度/模型，未检查命中圆环。符合测量条件就`step++`，网页随阶段自动换目标，没有用户确认。用户尚在追目标时就可能进入反方向下一步。 | 缺少投诉瞬间的网页目标坐标、pointermove和原生阶段联合轨迹，不能断言每次跳动都由此造成。 |
| 圆环还有隐藏的重新放置入口（实现/设计） | 0.2.13 `place()`由新阶段、新会话、首次基线、首次pointermove、视口resize触发。首次pointermove会从默认中央改成当前指针加方向距离；目标坐标又被限制在20%–80%宽、38%–78%高。它使用网页最近坐标，不是原生已验证基线。 | 基线丢失/恢复已不再每次重放目标，但首次pointermove例外仍在。钳制边缘可能缩短或改变引导方向；本次未记录实际发生次数。 |
| “身份”门禁与停稳互相牵制（设计/能力边界） | Tracker首次锁定要求唯一箭头、多帧、射线和箭头都移动且同向；采样又要求可信指针、输入空闲、稳定端点。任何不可信观察都会`invalidateSegment()`清除起点和累计报告。用户停稳等识别、识别又等相关移动，形成体验上的等待循环。 | 门禁不是账号验证，也不是数学上永远无法满足。此次缺候选序列，不能区分轮廓不匹配、多个候选、失锁还是时间过旧各占多少。 |
| 自然动作被测量规则拒绝（设计） | 轴向报告横向偏差需≤15%，位移门槛、350ms输入间隔及450ms稳定窗叠加；四方向慢/快共8段，再两段验证，最后还要对尖端确认。两条拒绝日志确实存在。 | 拒绝合并了方向、幅度等原因，没有记录各分量与门槛，不能证明是用户移动短、斜或某一检测失误。 |
| 无识别时超时失效（明确实现问题） | `observe()`先在不可信时return，180秒超时检查在后面。持续不可信时不会走到超时处理。 | 未取得本次超过180秒且持续不可信的完整轨迹；代码缺陷成立，不能据此断言这轮正是该情况。 |
| 模式状态误导（交互/引导） | 向导激活时自动对齐暂停，点拖等受限；0.2.11用户把“开关开”理解为跟随有效。0.2.12增加互斥提示，但没有减少流程负担。“身份未确认”也误导成认证问题。 | 不能通过只换词解决输入与识别依赖。之后不应再反复让用户开已经确认开启的开关。 |
| 顶部换行挤压视频（明确布局问题） | 原生状态原用wrap_content，视频按剩余空间分配；`fitVideo()`在尺寸改变时重设视频/射线布局并取消观察。0.2.13固定一行，设备读取高度56px，浏览器长文也不改区域坐标。 | 没有投诉时的连续layout/Surface事件，不能把所有目标跳动或Surface重建都归因于换行。该修复未解决追圈规则。 |

检测器目前只匹配少数小箭头轮廓。iPad原生指针会变成圆点、文本光标或与控件结合；这是已知能力边界，不能包装成通用可靠识别。[Apple官方行为说明](https://support.apple.com/en-us/105004)

## 我们的交付问题

1. 把理想数据上的38项单测、安装成功、页面能打开作为反复交付依据，却没有完整真实输入体验证据。虽然说明过测试边界，也仍把探索成本转给了用户。
2. 0.2.11修入口、0.2.12加底板、0.2.13修换行，都围绕同一个复杂流程打补丁，没有及时撤回失败的十步设计。
3. 状态日志数量多但信息不够：`RayAlignment`状态变化日志及约每秒观察日志会重复描述同一受阻状态；它们是INFO，不等于崩溃。缺少统一会话/阶段/基线版本、目标生成原因、分项拒绝值，使复盘无法可靠关联。减少日志不等于修复问题。

## 修复顺序与验收门槛

**P0：恢复简单直接操作。** 撤下追圈向导的默认入口，直接鼠标控制不依赖视觉识别或校准。保留一键“恢复直接控制”用于退出向导/关闭纠偏/重置本地输入状态，名字不能写“真实指针回中”。验收：没有识别结果时移动、点击、滚动仍可用；恢复操作本身不发鼠标移动或点击；不得暗中再进向导。

**P0：等待覆盖层用同一事实来源。** 先记录当前owner、Surface有效性、提交/呈现帧与waiting决策的同一时间快照，再针对失败路径修复。验收：当前Surface有确认缓冲时无waiting；新Surface尚未呈现不能借旧帧隐藏提示；暂停/恢复/窗口和PiP转换均检查。不得用重启掩盖现场。

**P1：精确功能可选且失败不阻断。** 不再让用户按识别门禁追移动圆环。若后续保留少量明确测量，目标在一个步骤内固定，失锁不重放，不自动推进；由用户明确确认阶段，必须先用真实输入回放验证。现在停止新增自然学习或另一套向导。

**P1：回中要有真实语义。** 跨应用绝对回中目前没有可靠接口证据；不做边缘撞墙后猜半屏。底板内pointer事件可作为该页专用反馈的研究候选，但必须先完成实际事件新鲜度、坐标映射、时序与有限命令验证，不能宣称已经实现，也不能冒称跨应用能力。用户此刻不承担新实验测试。

**P1：可复盘而非刷屏。** 分项记录拒绝原因，按同一会话中的持续故障统计次数/持续时间；明确区分失锁、重取基线、阶段变化和目标重放。日志只含必要数值与状态，不外发原始私密画面。必要诊断完成后再限制重复输出。

## 借鉴成熟产品的具体边界

Moonlight明确区分相对触控板与点选位置的触控模式，并提供退出输入捕获的快捷操作；借鉴的是模式清楚、退出简单。[官方操作指南](https://github.com/moonlight-stream/moonlight-docs/wiki/Setup-Guide#keyboardmousegamepad-input-options)

Virtual Desktop官方版本记录明确修正射线交会不应阻止物理鼠标；它依赖PC/Mac Streamer。Immersed要求电脑Agent，鼠标跨屏位置由电脑显示器排列决定。查到的主源不足以证实它们有可直接复用的“Quest把iPad鼠标回中”流程，不编造该能力。[Virtual Desktop版本记录](https://github.com/guygodin/VirtualDesktop/releases/tag/v1.34.8) · [Virtual Desktop平台要求](https://www.vrdesktop.net/) · [Immersed FAQ](https://immersed.com/faq)

Sunshine绝对坐标由被控电脑平台注入，Apple通用控制依赖Mac与iPad，FaceTime远控依赖获准的系统通话。这些是不同主机能力，不是给现有相对BLE HID增加一个按钮就能复制。[Sunshine实现](https://github.com/LizardByte/Sunshine/blob/master/src/input.cpp) · [Apple通用控制](https://support.apple.com/en-euro/guide/ipad/ipad3924226c/ipados) · [FaceTime远控](https://support.apple.com/en-gb/guide/ipad/ipada92df253/ipados)

推荐收敛为：**连接 → 启用直接控制 → 正常使用；不正常时恢复直接控制。** 视觉辅助在可选设置中，不作为用鼠标的前提。这个方案仍需实现与验证，当前未装新版本，也没有完成真实回中。
